# Design: LH/SH 임대공고 뷰어 + 내 조건 알림

## Problem Statement
LH·SH 임대공고를 사이트마다 들어가 확인하기 번거롭다. 한 화면에서 목록을 보고, 내가 지원할 수 있는 새 공고가 올라오면 카카오톡으로 바로 알림받고 싶다.

## What Makes This Cool
매일 오전 9시(KST)에 전날 이후 새 공고를 카톡으로 한 번에 받는다. 같은 제목(정정·재공고 포함)은 다시 보내지 않는다. GitHub cron은 정시보다 수~수십 분 늦을 수 있다. 마감일(D-day)과 바로가기 버튼이 함께 와서, 알림을 누르면 공고문으로 바로 이동한다. 운영비는 0원이다(GitHub Actions, Vercel Hobby, 카카오 나에게 보내기).

## Constraints
- 의존성 0개, Node 20 내장 fetch만 사용 (기존 봇과 같은 방식).
- 알림 채널은 카카오 "나에게 보내기". 알림톡은 사업자등록과 유료 발송대행이 필요해서 제외.
- Vercel Hobby cron은 하루 1회만 돌아서, 알림은 GitHub Actions에 둔다(2026-09-23 변경: 30분 주기 → 매일 09:00 KST).
- 레포는 `hyun-june/lease-notice` 공개. 시크릿은 GitHub Secrets에 둔다.
- LH 데이터는 서드파티 프록시(`k-skill-proxy.nomadamas.org`)를 거치고, SH 데이터는 i-sh.co.kr HTML을 스크래핑해서 가져온다.

## Premises (사용자 동의)
1. 지역 필터만으로는 부족하다. 2026-09-23 기준 LH 공고중 124건 중 서울·경기·인천 약 33건이고, 그중 16건이 토지·임대상가다. 그래서 LH는 **지역 + 임대주택 유형**으로 거른다. 유형 규칙은 이름에 "임대"가 들어가고 "상가"는 없는 것이다. 국민·행복·매입·영구·공공·통합공공임대와 "분양전환 공공임대"(임대 후 분양전환)는 남는다. "분양주택", "토지", "임대상가(입찰)"는 빠진다.
2. 지역이 "전국"인 공고는 지역 조건을 통과한 것으로 친다. 유형 조건은 그대로 적용한다.
3. 나이·소득 같은 자격 조건은 자동으로 판단하지 않는다. 공고문이 PDF라 파싱이 부정확하다. 자격은 알림을 받은 뒤 직접 확인한다.
4. 알림은 GitHub Actions에서 매일 09:00 KST에 돌리고, Vercel은 목록 뷰어만 맡는다.

## Approaches Considered
- A) 최소 변경: 봇에 필터만 추가하고 뷰어는 함수 하나로 감싼다. 파싱 코드 중복이 남고 "내 조건" 탭이 없어서 제외.
- C) 정적 스냅샷: Actions가 notices.json을 커밋하고 뷰어는 그 파일만 읽는다. 키워드 검색과 다른 SH 게시판 탭이 사라져서 제외.

## Recommended Approach (선택: B, 공통 모듈 + API)
- `config.json`: `{"regions":["서울특별시","경기도","인천광역시"]}`. 바꿀 때는 GitHub 웹에서 파일을 수정한다.
- `lib.js`: 기존 두 파일에 중복된 SH_BOARDS, shUrl, shDetail, text, parseSh, ymd를 옮기고, 필터 규칙을 한 곳에 모은다.
  - `loadConfig()`: config.json을 읽는다. JSON이 깨졌거나 regions가 배열이 아니거나, 알려진 시도명(뷰어의 지역 목록과 같은 17개)이 아닌 값이 있으면 예외를 던진다.
  - `lhMine(item, regions)`: 지역(`cnp_cd_nm`)이 regions 중 하나를 포함하거나 "전국"이고, 유형(`ais_tp_cd_nm`)에 "임대"가 있고 "상가"가 없을 것. regions가 비어 있으면 지역 조건을 건너뛴다.
  - `shOn(regions)`: regions가 비었거나 "서울특별시"를 포함하면 true. SH는 **주택임대 게시판(multi_itm_seq=2) 1페이지**만 본다. 게시판 자체가 서울 임대라서 유형 필터는 적용하지 않는다.
  - `node lib.js`로 실행하면 assert 기반 자체 검사가 돈다(샘플 공고로 규칙 확인).
- `notify.js`: LH는 `lhMine`을 통과한 공고만 seen과 비교한다. 필터에서 빠진 공고는 seen에 기록하지 않는다. SH는 `shOn`일 때만 조회한다. 나머지 동작은 기존 그대로다.
- `api/lh.js`, `api/sh.js`: Vercel Node 함수. 기존 로컬 서버의 `/api/lh`, `/api/sh`와 똑같이 동작한다. 입력은 검증한다. SH 게시판 값은 SH_BOARDS 키만 허용(아니면 주택임대), page는 1~100 정수, 키워드는 URLSearchParams로 인코딩한다. LH 파라미터도 허용 목록(q, uppAisTpCd, panSs, cnpCdNm, pageSize)만 넘긴다. 따라서 요청은 고정된 두 호스트로만 나간다.
- `api/mine.js`: "내 조건" 목록을 서버에서 만든다. `loadConfig` → LH 공고중 목록 조회 → `lhMine` 필터, `shOn`이면 SH 주택임대 1페이지 → 날짜 내림차순으로 합쳐 반환한다. 브라우저에 필터 규칙을 복사하지 않으므로 알림과 뷰어의 규칙이 어긋날 수 없다.
- `index.html`: 기존 뷰어 페이지에 "내 조건" 탭을 기본으로 추가한다. 이 탭은 `/api/mine`만 호출한다. 기존 LH·SH 전체 검색 탭은 그대로 둔다.
- 상위 폴더의 로컬 뷰어(`임대공고보기.js`, `.command`)는 삭제한다.
- LH 목록 조회: 프록시에 `pageSize=1000`을 주면 한 번에 전부 온다. 2026-09-23 기준 공고중 124건이 한 응답에 왔다. 결과 수가 1000건에 닿으면 경고 로그를 남긴다.

### 운영 동작 (대부분 기존 봇 그대로이고, 바꾸는 곳은 "(변경)"으로 표시)
- **카카오 토큰**: 실행할 때마다 refresh_token으로 access_token을 새로 받는다. 카카오가 refresh_token을 새로 주면 `GH_PAT`(fine-grained PAT, 이 레포 Secrets 쓰기 권한)로 `KAKAO_REFRESH_TOKEN` 시크릿을 덮어쓴다. PAT가 만료되면 이 갱신이 실패한다. 이때 Actions 실행이 실패로 표시되고 GitHub이 메일로 알린다. README에 PAT 만료일을 캘린더에 적어 두라는 안내가 있다.
- **seen 상태**: `seen.json`을 레포에 커밋한다. 워크플로에 `concurrency: notify` 그룹이 있어 실행이 겹치지 않는다. 사용자가 웹에서 config.json을 고친 직후에 봇이 push하면 충돌이 날 수 있어서, 커밋 스텝에 `git pull --rebase` 후 push를 추가한다(변경).
- **조회 실패**: LH나 SH 조회가 실패하면 그쪽은 빈 목록으로 처리되고 seen은 바뀌지 않는다. 다른 쪽 알림은 정상 발송된다. 조회를 시도한 쪽이 모두 실패하거나 0건이면(SH를 조회하지 않는 설정이면 LH만 기준) `process.exit(1)`로 실행을 실패 처리해서 GitHub 메일 알림이 가게 한다(변경). 지금은 경고 로그만 남긴다.
- **발송 상한**: 한 번에 최대 5건을 보내고, 넘는 건은 "외 N건 더 있음" 요약 1건을 보낸다. 요약 발송에 성공하면 나머지 공고도 seen에 기록한다. 요약 버튼은 LH 목록으로 연결된다. 나머지는 뷰어 "내 조건" 탭에서 확인한다.
- **60일 비활성 정지**: 공개 레포의 예약 워크플로는 60일 동안 레포 활동이 없으면 GitHub이 꺼 버린다. seen.json 커밋이 활동으로 잡히지만, 신규 공고가 60일 동안 0건이면 꺼질 수 있다. 꺼지기 전에 GitHub이 메일을 보낸다.
- **카카오 도메인**: 알림 버튼 링크는 apply.lh.or.kr, www.i-sh.co.kr로만 연결된다. 두 도메인은 README 설정 4단계에서 이미 등록한다. Vercel 도메인으로 가는 링크는 넣지 않는다.
- **config 검증 위치**: 워크플로의 notify 앞에 `node lib.js`(자체 검사)를 넣는다. notify.js는 시작할 때 `loadConfig()`로 설정을 검증하고, 문제가 있으면 실패로 끝낸다.

## Open Questions
- `/api/*`는 누구나 호출할 수 있다. 입력을 검증하므로 임의 URL을 대신 호출하는 데 쓸 수는 없다. 트래픽 제한은 두지 않는다(개인용).
- 지역을 새로 추가하면 기존 공고가 한꺼번에 신규로 잡힌다. 발송 상한 규칙(5건 + 요약)이 적용된다.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — completeness

**Problem**

> Under '조회 실패', the run fails only when every source it tried fails or returns 0. If just one side breaks, for example the SH HTML scrape after a markup change (the likeliest failure), that side is treated as an empty list and the run succeeds with only a log line, so SH notices stop arriving without any signal. The design also doesn't say what happens to seen.json when a fetch succeeds but returns 0 items: if seen is pruned to the current list, recovery would re-send everything.

**Remedy**

> Treat a failure or a 0-item result from any single source you tried as a visible failure. Send the other side's alerts first, then exit(1) or send a Kakao error message. State that a successful fetch with 0 items leaves that source's seen entries untouched.

### R2-2 — consistency

**Problem**

> Premise 1 says 행복주택 is kept, but the lhMine rule keeps only types whose ais_tp_cd_nm contains '임대'. LH type names include values such as '행복주택' and '장기전세' that don't contain '임대', so the substring rule would silently drop the housing types the premise says to keep.

**Remedy**

> Check the rule against the actual ais_tp_cd_nm values in the 2026-09-23 response of 124 notices. Then switch to an explicit whitelist of rental types, or filter on the upper type code (임대주택), and add 행복주택 and 장기전세 cases to the lib.js self-check.

### R2-3 — clarity

**Problem**

> The Distribution Plan registers '시크릿 3개' (3 secrets) but never names them. Kakao token handling also requires GH_PAT, a fine-grained PAT with Secrets write access. It's unclear whether GH_PAT is one of the three or a fourth secret, so setup could leave out the credential that token rotation needs.

**Remedy**

> List every secret by name (Kakao key(s), KAKAO_REFRESH_TOKEN, GH_PAT) with its required scope, and give the gh secret set command for each one.

### R2-4 — feasibility

**Problem**

> api/mine.js calls loadConfig(), which reads config.json from disk at runtime. On Vercel, files that are read through fs are only included in the function bundle if file tracing detects them. If the path isn't traceable, /api/mine fails in production even though it works locally.

**Remedy**

> State how config.json gets into the function: load it with require('./config.json'), use a statically traceable __dirname path, or set includeFiles in vercel.json. Also verify /api/mine on a preview deployment.

### R2-5 — clarity

**Problem**

> lib.js is imported by notify.js and by the api/* functions, and 'node lib.js' also runs the assert self-check. The design doesn't say the self-check runs only on direct execution. Without that guard, every notify run and every API cold start would execute the asserts, and a failure would crash production paths.

**Remedy**

> Specify that the self-check runs only under require.main === module (or an equivalent guard).

### R2-6 — feasibility

**Problem**

> Vercel auto-deploys on every push, and the bot pushes a seen.json commit to the same repo whenever new notices arrive, up to 48 times a day. Each of those commits triggers a pointless viewer redeploy, which uses up the Hobby build/deploy quota and clutters the deployment history.

**Remedy**

> Add a Vercel Ignored Build Step that skips deployments where only seen.json changed, or store the seen state somewhere that doesn't trigger deploys.

### R2-7 — consistency

**Problem**

> The Distribution Plan says the existing .github/workflows/notify.yml is used as is ('그대로 쓴다'). However, '운영 동작' and Next Steps step 3 change that workflow by adding the self-check step and git pull --rebase before push.

**Remedy**

> Rewrite the Distribution Plan line to say the workflow is modified, and list the changes (self-check step, pull --rebase, GH_PAT use).

### R2-8 — consistency

**Problem**

> A Success Criterion says the workflow runs the same checks as local: node --check on every js file plus node lib.js. '운영 동작' ('config 검증 위치') adds only node lib.js before notify, so the node --check part is never assigned to the workflow.

**Remedy**

> Either add a node --check step for all js files to the workflow change list, or narrow the Success Criterion to say the workflow runs only node lib.js.

### R2-9 — clarity

**Problem**

> The viewer's '내 조건' tab is the default tab and calls only /api/mine. The design doesn't define what /api/mine returns, or what the tab shows, when loadConfig throws (for example after a bad config.json edit in the GitHub web UI, which also triggers a redeploy) or when the LH proxy or SH scrape fails. The user could see a blank list that looks like 'no matching notices'.

**Remedy**

> Specify /api/mine's error response: a status code plus which source failed, and partial results when only one side fails. Specify that the tab shows a clear error or partial-data banner instead of an empty list.

### R2-10 — clarity

**Problem**

> The overflow summary's button always opens the LH list, but the overflow can include SH notices, which are marked seen as soon as the summary is sent. For SH overflow, the button leads to the wrong site, and the only way to find those notices is to open the viewer, which the message can't link to.

**Remedy**

> Say how SH overflow is reached. For example, include LH and SH counts in the summary text and add a second button to the SH board, or state explicitly that the user must open the viewer.

### R2-11 — consistency

**Problem**

> loadConfig validates regions against 'the same 17 names as the viewer's region list', which means the list exists both in index.html and in lib.js. Nothing keeps the two copies in sync, which is the same drift risk that api/mine.js was introduced to remove.

**Remedy**

> Keep the 17-region list in one place, for example exported from lib.js and served to the viewer by an API or build step, or name one copy as the source of truth and have the self-check compare them.

### Prior finding evidence

**R1-4 → R2-1 (persisting)**

> '조회 실패' fails the run only when every source it tried fails or returns 0, so a single broken source (for example an SH format change) is still silent. seen handling for a successful fetch with 0 items is undefined.
